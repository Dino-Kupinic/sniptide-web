## Run it

Start your app on `localhost:3000` and install Caddy 2. For public HTTPS, point both domain names at the server and allow incoming TCP traffic on ports 80 and 443. Remove the `www` block if you only have DNS for the bare domain.

With the official systemd service, save the file at `/etc/caddy/Caddyfile`, then validate and reload.

```bash title="Terminal"
sudo caddy validate --config /etc/caddy/Caddyfile --adapter caddyfile
sudo systemctl reload caddy
```

Replace `example.com` in this check and expect a redirect to `https://example.com/` followed by your app's response.

```bash title="Terminal"
curl -sS -D - -o /dev/null http://example.com/
curl -fsS https://example.com/
```

Caddy obtains and renews certificates automatically for public site names. If HTTPS fails, check DNS for both names and inspect `sudo journalctl -u caddy -n 50`. [Caddy automatic HTTPS](https://caddyserver.com/docs/automatic-https)

## What each part does

| Part | What it does | When to change it |
| --- | --- | --- |
| `example.com` | A site block. A domain name as the address turns on HTTPS and the redirect from HTTP. | Use your domain. List several, separated by commas, to serve them the same way. |
| `encode` | Compresses responses with zstd or gzip, whichever the browser accepts. | Rarely. |
| `reverse_proxy` | Sends every request to your app. Caddy sets `X-Forwarded-For` and `X-Forwarded-Proto` for it. | Point it at your app's address and port. |
| `header` | Adds security headers. `-Server` removes Caddy's own `Server` header. | Add a `Content-Security-Policy` once you know which sources your app loads. |
| `log` | Enables site access logs on standard error. | Read them in the systemd journal or with `docker compose logs caddy`. |
| `www.example.com` | Redirects the www name to the bare domain, keeping the path. | Swap the two if you prefer www. |

If you add `Strict-Transport-Security`, start with a short `max-age` after HTTPS is stable. Use `includeSubDomains` only when every subdomain can serve HTTPS.

## Variant: Caddy in Docker Compose

Save these two files together beside the app's Dockerfile. The app must listen on `0.0.0.0:3000` inside its container. Run `docker compose up -d --build` and use the HTTPS check above. Use `docker compose down` to stop the stack and retain certificates in `caddy_data`.

```yaml title="compose.yaml"
services:
  caddy:
    image: caddy:2
    restart: unless-stopped
    ports:
      - "80:80"
      - "443:443"
      - "443:443/udp"
    volumes:
      - ./Caddyfile:/etc/caddy/Caddyfile:ro
      - caddy_data:/data
      - caddy_config:/config

  app:
    build: .

volumes:
  caddy_data:
  caddy_config:
```

```text title="Caddyfile"
example.com {
	reverse_proxy app:3000
}
```

## Variant: an API and a front end on one domain

`handle_path` strips the matched prefix before proxying, so the API sees `/users` for a request to `/api/users`. The `/api/*` pattern matches paths below `/api/`. Add an explicit redirect for bare `/api` if clients use it, or use `handle` with a named matcher to keep both paths and their prefixes.

```text title="Caddyfile"
example.com {
	handle_path /api/* {
		reverse_proxy localhost:4000
	}

	handle {
		reverse_proxy localhost:3000
	}
}
```

## Variant: several app servers

List more than one upstream and Caddy balances between them, skipping any that fail their health check.

```text title="Caddyfile"
example.com {
	reverse_proxy app1:3000 app2:3000 {
		lb_policy round_robin
		health_uri /api/health
		health_interval 10s
	}
}
```
