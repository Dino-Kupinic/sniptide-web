## Set up the issue chooser

1. Enable Issues. Create the `bug`, `triage` and `enhancement` labels, or replace them in the forms.
2. In `config.yml`, replace `YOUR-OWNER/YOUR-REPO`. Keep the Discussions link if you have enabled Discussions. Keep the advisory link if private vulnerability reporting is enabled, or point it to your private reporting channel.
3. Merge the files into the default branch. Open **Issues → New issue**, confirm both forms and each contact link appear, and try submitting a form with a required field left blank.

GitHub enforces the required fields in the form UI. [Issue form syntax](https://docs.github.com/en/communities/using-templates-to-encourage-useful-issues-and-pull-requests/syntax-for-issue-forms)

## What each file does

| File | What it does |
| --- | --- |
| `bug_report.yml` | Asks what happened, how to reproduce it and which version, and adds the `bug` and `triage` labels. |
| `feature_request.yml` | Asks for the problem before the solution, and how often it happens, which is what you need to prioritize. |
| `config.yml` | Turns off blank issues and links to Discussions for questions and to GitHub's private vulnerability reporting flow. |

## The fields you'll change

| Key | What it does | Note |
| --- | --- | --- |
| `name`, `description` | The choice people see on the New issue page. | Keep the description to the one case the form is for. |
| `title` | Pre-fills the issue title. | A prefix such as `[Bug]: ` makes the list scannable. |
| `labels` | Labels added on submit. | Create the labels in the repository first. |
| `type` | The field: `markdown`, `textarea`, `input`, `dropdown` or `checkboxes`. | `markdown` shows text and collects nothing. |
| `render` | Formats a `textarea` as a code block. | Use it for logs, so nobody has to add the fences. |
| `validations.required` | Blocks submit until the field is filled. | Require only what you can't triage without. Every extra required field loses reports. |

## Ask for the problem first

The feature form asks "What problem would this solve?" before "What would you like to happen?". Keep the proposed solution optional so someone can report a problem even when they have no fix in mind.

Once an issue is accepted, rewrite it as a [user story](/templates/user-stories) with acceptance criteria before anyone builds it.

## Variant: a pull request template

Pull requests use a Markdown file rather than a form. Put it at `.github/pull_request_template.md`:

```md title=".github/pull_request_template.md"
## What this changes

## How I tested it

- [ ] Tests added or updated
- [ ] Docs updated
```
