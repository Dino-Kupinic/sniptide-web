## Turn on standalone output

Use Docker with BuildKit and a single-package Next.js app with a committed `pnpm-lock.yaml`, a `packageManager` entry pinning pnpm, and a `build` script that runs `next build`. Add `output: "standalone"` to your existing Next.js config. [Next.js standalone output](https://nextjs.org/docs/app/api-reference/config/next-config-js/output)

```ts title="next.config.ts"
import type { NextConfig } from "next"

const nextConfig: NextConfig = {
  output: "standalone",
}

export default nextConfig
```

The build produces `.next/standalone/server.js` and the traced server dependencies. The image also copies static assets and `public/`. The build creates an empty `public/` for projects without one. Workspaces may emit `server.js` under an app-specific subdirectory and need their own copy paths and tracing root.

```bash title="Terminal"
docker build -t my-app .
docker run --rm -p 127.0.0.1:3000:3000 my-app
```

Open http://localhost:3000 and check that the page and its static assets load. Press Ctrl+C to stop the container.

## What each stage does

| Stage | What it does | When to change it |
| --- | --- | --- |
| `base` | Node 24 on Alpine. The image installs Corepack explicitly, then uses the pnpm version from `packageManager`. | When you move to a new Node version. |
| `deps` | Installs dependencies from the lockfile alone, so Docker reuses this layer until the lockfile changes. The cache mount keeps pnpm's store between builds. | When you switch package managers, as in the variant below. |
| `build` | Copies the source and runs `pnpm build`. | When the build needs variables, as described below. |
| `runner` | A fresh image with only the standalone server, the static files and `public`. It runs as the `nextjs` user. | Rarely. |

`HOSTNAME=0.0.0.0` makes the server listen on every interface inside the container. This lets Docker's published port reach the server inside the container.

The `.dockerignore` keeps local dependencies, previous builds and files beginning with `.env` out of the build context. For native modules that require glibc, switch both Node images to `node:24-bookworm-slim` and use Debian's `groupadd` and `useradd` in the runner.

## Variables at build time and run time

Add `--env-file .env` before the image name if the app needs runtime variables. Code that runs during static generation needs its inputs during the build. For build-time secrets, use BuildKit secret mounts and keep the values out of rendered pages.

Variables that start with `NEXT_PUBLIC_` are written into the JavaScript bundle during `pnpm build`. They must exist in the build stage:

```dockerfile title="Dockerfile"
FROM base AS build
ARG NEXT_PUBLIC_APP_URL
ENV NEXT_PUBLIC_APP_URL=$NEXT_PUBLIC_APP_URL
COPY --from=deps /app/node_modules ./node_modules
COPY . .
RUN mkdir -p public && pnpm build
```

Then build with `docker build --build-arg NEXT_PUBLIC_APP_URL=https://example.com -t my-app .`. Only public values belong in a build argument, because anyone can read them from the image.

## Variant: npm

Replace the `base` and `deps` stages, and run `npm run build` in the build stage.

```dockerfile title="Dockerfile"
FROM node:24-alpine AS base
WORKDIR /app

FROM base AS deps
COPY package.json package-lock.json ./
RUN --mount=type=cache,target=/root/.npm npm ci
```

## Variant: Bun

Bun can install and build, while the standalone server still runs on Node. Replace the `base`, `deps` and `build` stages with these stages. Keep the build and runtime images on the same libc family by using the Alpine Bun tag.

```dockerfile title="Dockerfile"
FROM oven/bun:1-alpine AS deps
WORKDIR /app
COPY package.json bun.lock ./
RUN bun install --frozen-lockfile

FROM oven/bun:1-alpine AS build
WORKDIR /app
COPY --from=deps /app/node_modules ./node_modules
COPY . .
RUN mkdir -p public && bun run build
```

Keep the `runner` stage from the template as it is. To run the app with Docker Compose next to a database, use the [Docker Compose Postgres template](/templates/docker-compose-postgres).
