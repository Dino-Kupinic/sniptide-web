## Why a PRD for an agent reads differently

Write down the choices a teammate would otherwise ask about. In this export example, that means which rows count across pages, which workspace they belong to, how each column is formatted, and what happens at 10,001 rows.

Keep the file in the repository, such as `docs/specs/`, so the agent can read it next to the code and the spec changes in the same pull request as the feature.

## What each section does

| Section | What it gives the agent | How to write it |
| --- | --- | --- |
| Problem | The reason behind the feature, which settles small choices the spec doesn't cover. | Who hurts, how often, what it costs today. |
| Goal | One sentence of the outcome, and how you'll know it worked. | A user-visible result, not a list of tasks. |
| Users and stories | Who the feature is for and which permissions matter. | One story per role that behaves differently. |
| Requirements | The behavior, one checkable statement per number. | Exact names, formats, limits and orders. Numbers let you say "requirement 6 is wrong" in review. |
| Out of scope | The work the agent must not start. | Name the features people will assume come along. Agents tend to add them. |
| Technical notes | Where the change goes and what to reuse. | File paths and function names. This stops a second copy of logic that already exists. |
| Acceptance criteria | The tests the agent writes and runs before it says it's done. | Concrete inputs and expected results, including the awkward ones. |
| Decisions and open questions | What is settled and what still needs an owner. | Record decisions and mark unresolved questions that block implementation. |

Map the checks to the requirements. Include an authorized request, a forbidden request and examples on both sides of a limit. For exports opened in spreadsheets, check how the file handles user-entered values that look like formulas. [OWASP CSV injection guidance](https://owasp.org/www-community/attacks/CSV_Injection)

## Hand it to the agent

Replace the sample paths with modules you have checked in your codebase. Give the agent the spec and ask it to flag mismatches before implementation.

```text title="Prompt"
Read docs/specs/csv-export.md and compare it with the invoice list and authorization code.
Map each requirement to a test. Flag any conflict with the current behavior or missing decision.
```

Rules that apply to every task, such as commands and code style, belong in your [AGENTS.md](/templates/agents-md) or [CLAUDE.md](/templates/claude-md) rather than in each spec.

## Variant: a one-page spec for a small change

A bug fix or a small feature needs only three sections. Keep the acceptance criteria even when everything else goes.

```md title="docs/specs/empty-state.md"
# Empty state on the Invoices page

## Requirements

1. When a workspace has no invoices, the list shows the `EmptyState` component from
   `components/ui/empty-state.tsx` instead of an empty table.
2. Title: "No invoices yet". Help text: "Create your first invoice to see it here."
   Action: a **New invoice** button that opens `/invoices/new`.
3. With filters set and no matches, show "No invoices match these filters" and a
   **Clear filters** button instead.

## Out of scope

- Illustrations or animation.

## Acceptance criteria

- [ ] A new workspace shows the empty state with the button.
- [ ] A workspace with invoices but no matches shows the filter message.
```
