The Sniptide blog lives in the same repository as the marketing site. A post is one MDX file in
`content/blog`, it goes through a pull request like any other change, and it ships when the site
deploys. This post walks through how that works, and it uses every component a post can use, so it
doubles as the reference for the next one.

## Why posts are files in the repository

We looked at a headless CMS and at hosted blogging platforms, and both added a service to run for a
team that writes a few posts a month. Files in git keep the review, the history and the preview
deploys we already have for code. They also let a coding agent draft a post the same way it drafts
any other change, which matters for a product built around agents.

<Callout type="tip" title="Drafts stay out of production">
  Set `draft: true` in the frontmatter while you write. The post renders in `next dev`, and
  production builds leave it out of the index, the sitemap and the feed.
</Callout>

## Write a post

<Steps>
  <Step>
    ### Create the file

    The file name becomes the address, so `content/blog/agent-recipes.mdx` is served at
    `/blog/agent-recipes`. Use lowercase words joined by hyphens.
  </Step>
  <Step>
    ### Fill in the frontmatter

    The schema in `lib/blog.ts` checks every field when the site builds, so a missing description
    or an unknown author fails the build instead of shipping a broken page.

    ```yaml title="content/blog/agent-recipes.mdx"
    ---
    title: Teach your agent a recipe
    description: Collections give a coding agent an ordered set of snippets to follow.
    date: 2026-11-20
    author: dino
    category: agents
    tags: [collections, mcp]
    draft: true
    ---
    ```
  </Step>
  <Step>
    ### Preview it

    Run the site locally and open the post. Press <Kbd>⌘</Kbd> <Kbd>R</Kbd> after an edit if the
    page doesn't refresh on its own.
  </Step>
</Steps>

## The frontmatter fields

<Params>
  <Param name="title" type="string" required>
    The headline. It also sets the browser tab, the search result and the Open Graph card, so it
    stays under 70 characters.
  </Param>
  <Param name="description" type="string" required>
    One sentence of 50 to 160 characters. It is the line on the index, the search snippet and the
    feed summary.
  </Param>
  <Param name="date" type="YYYY-MM-DD" required>
    The day the post is published. The index sorts by it, newest first.
  </Param>
  <Param name="updated" type="YYYY-MM-DD">
    The day of the last meaningful change. The sitemap and the structured data use it.
  </Param>
  <Param name="author" type="string" required>
    A key from `lib/authors.ts`, which holds the name, role and avatar.
  </Param>
  <Param name="category" type="string" required>
    One of `product`, `engineering`, `agents`, `self-hosting` or `company`. The index filters by
    it, and it sits next to the date.
  </Param>
  <Param name="tags" type="string[]" default="[]">
    Lowercase words that show at the end of the post, in the feeds and in search.
  </Param>
  <Param name="image" type="string">
    A path under `public/` that replaces the generated Open Graph card.
  </Param>
  <Param name="draft" type="boolean" default="false">
    Keeps the post out of production builds.
  </Param>
</Params>

## Code in a post

Fenced code blocks get the same colours as a paste in the app, in light and dark. A `title` puts
the file name above the code.

```ts title="lib/blog-source.ts"
export function getPost(slug: string): Post | undefined {
  return getPosts().find((post) => post.slug === slug)
}
```

When a reader picks one of several options, such as a package manager, put the alternatives in
tabs.

## Tables, lists and quotes

Plain Markdown covers the rest. Numbers in tables use tabular figures and align right.

| Surface | Reads the post from | Updates |
| --- | --- | --: |
| The post page | The compiled MDX | Every deploy |
| `/blog/rss.xml`, `atom.xml`, `feed.json` | The frontmatter | Every deploy |
| `/blog/<slug>.md` | The processed Markdown | Every deploy |

A few habits keep posts consistent:

- Write full sentences, and keep one idea to a paragraph.
- Link to the docs for setup steps instead of repeating them.
- Say what Sniptide does not do when a claim could be read too broadly.

> Every word, element and decoration earns its place, and anything that does not gets removed.

<Callout type="warning" title="Check both themes">
  Open the post in light and dark before you ask for a review. Pictures and diagrams are the parts
  that most often look wrong in one of them.
</Callout>

<Callout title="Every post has a Markdown twin">
  Add `.md` to a post's address to read it as plain Markdown. Agents and feed readers use it, and
  `llms.txt` points to the feed.
</Callout>
