A `.env` file is a plain text file of `KEY=value` lines that holds a project's configuration, such as its port, database address and API keys. There is no formal standard for it, so we wrote 17 small files, each with one line people commonly get wrong, and loaded every one with 11 loaders, from dotenv and Next.js to Go, Bash and Docker Compose. All 11 agreed on 6 of the files and split on the other 11.

## How we ran the test

On 17 November 2026 we wrote each case into its own `.env` file and loaded it with these 11 loaders. Each loader ran from an empty environment, so nothing from our own shell could leak in, and printed the values it set as JSON.

| Loader | Read with |
| --- | --- |
| dotenv 18.0.10 | `config()` |
| Node.js 22.23.4 | `--env-file` |
| Bun 1.4.4 | `--env-file` |
| Next.js, `@next/env` 16.4.6 | `loadEnvConfig()` |
| Vite 8.3.8 | `loadEnv()` |
| Deno 2.9.6 | `--env-file` |
| Ruby dotenv 3.2.0 | `Dotenv.load` |
| python-dotenv 1.2.3 | `load_dotenv()` |
| Go godotenv 1.5.1 | `godotenv.Load()` |
| GNU Bash 5.2.21 | `set -a; . ./.env` |
| Docker Compose 5.6.1 | `env_file` |

Compose doesn't start a container for this: `docker compose config` prints the environment each service would get.

Download [all 17 test files](/blog/env-file/loader-tests.zip) to rerun the cases with your own loader. Each folder holds one `.env` and a `compose.yaml`.

## How a .env file reaches your app

Your code never reads the file. The operating system gives each process an environment, a list of names and values inherited from whatever started it, and a loader reads the file once at startup and adds its lines to that list. The app then reads `process.env.PORT` or `os.environ["PORT"]`.

Each loader brings its own parser, which is why the same file can produce different values. It also means an edit to `.env` does nothing until the app restarts, and every value arrives as a string, so `PORT` is `"3000"` and `DEBUG=true` is the text `"true"`.

## What all 11 loaders agree on

Six of the 17 files read the same in every loader:

| Line | Every loader read |
| --- | --- |
| `PORT=3000 # dev server` | `3000` |
| `HASH="abc#123"` | `abc#123` |
| `export PORT=3000` | `3000` |
| `SENTRY_DSN=` | An empty string |
| `NAME=acme   ` | `acme` |
| A multi-line PEM key in double quotes | The same lines |

A space before `#` starts a comment everywhere, trailing spaces are trimmed, and an empty value sets the variable to an empty string, which is different from leaving the line out.

## Where the loaders disagree

The other 11 files produced at least two different results. Bash read 7 of them differently from most of the other loaders, mostly because it runs the file as shell code instead of parsing it. No other loader stood apart on more than 3.

Each section below shows the line we tested and what each loader made of it.

### Spaces in an unquoted value

```bash title=".env"
APP_NAME=Acme notes
```

| Loader | `APP_NAME` |
| --- | --- |
| Every loader except Bash | `Acme notes` |
| Bash | Unset |

Bash reads the line as a command: it sets `APP_NAME=Acme` for a program called `notes`, which doesn't exist, so the variable never reaches the environment. `APP_NAME="Acme notes"` works in all 11.

### A `#` inside an unquoted value

```bash title=".env"
HASH=abc#123
```

| Loader | `HASH` |
| --- | --- |
| dotenv, Node, Bun, Next.js, Vite, Deno, Ruby | `abc` |
| python-dotenv, Go, Bash, Compose | `abc#123` |

Seven loaders treat the `#` as the start of a comment, so a password containing `#` silently loses its end. With double quotes, `HASH="abc#123"` reads the same in all 11.

### A `$` inside single quotes

```bash title=".env"
PRICE='costs $5'
```

| Loader | `PRICE` |
| --- | --- |
| Bun, Next.js | `costs ` |
| The other nine | `costs $5` |

In most loaders single quotes turn expansion off. Bun and Next.js expand `$5` anyway, find no variable called `5`, and leave an empty string in its place.

### An escaped `$`

```bash title=".env"
PRICE="costs \$5"
```

| Loader | `PRICE` |
| --- | --- |
| dotenv, Node, python-dotenv | `costs \$5` |
| The other eight | `costs $5` |

Bun and Next.js document `\$` as the fix for the case above, but three loaders keep the backslash. Together with single quotes, we found no spelling of `$` that all 11 read the same. If a secret contains `$`, test it with the loader you deploy with.

### A reference to another variable

```bash title=".env"
API_BASE=https://api.example.com
API_URL=${API_BASE}/v1
```

| Loader | `API_URL` |
| --- | --- |
| dotenv, Node | Kept as text |
| The other nine | Expanded |

The nine expand it to `https://api.example.com/v1`, while dotenv and Node pass `${API_BASE}/v1` through unchanged. The dotenv package needs its companion `dotenv-expand` for this, and Node's flag doesn't expand at all. Writing the full value on each line works everywhere.

### `\n` in double quotes

```bash title=".env"
SIGNATURE="Line one\nLine two"
```

| Loader | `SIGNATURE` |
| --- | --- |
| Ruby dotenv, Bash | A literal `\n` |
| The other nine | Two lines |

Ruby dotenv and Bash keep the backslash and the `n` as two characters. A real line break inside the double quotes, as in the PEM key above, reads the same in all 11.

### Spaces around `=`

```bash title=".env"
PORT = 3000
```

| Loader | `PORT` |
| --- | --- |
| Every loader except Bash | `3000` |
| Bash | Unset |

Bash runs a command called `PORT` instead of assigning it. Leave the spaces out.

### The same name twice

```bash title=".env"
PORT=3000
PORT=3001
```

| Loader | `PORT` |
| --- | --- |
| Every loader except Deno | `3001`, the later line |
| Deno | `3000`, the first line |

This usually happens when someone appends an override to the bottom of the file. In Deno the override does nothing, so keep each name on one line.

### Windows line endings

The file `PORT=3000` and `APP=acme`, saved with CRLF line endings:

| Loader | `PORT` |
| --- | --- |
| Every loader except Bash | `3000` |
| Bash | `3000\r` |

Bash keeps the carriage return at the end of every value. The stray `\r` turns into a database name or port that looks right in a log and fails to match. Save the file with LF line endings, which most editors show in the status bar.

### A byte order mark

The same two lines, saved as UTF-8 with a byte order mark (BOM), an invisible character some Windows editors put at the start of the file:

| Loader | `PORT`, the first line |
| --- | --- |
| dotenv, Bun, Next.js, Ruby, python-dotenv, Compose | `3000` |
| Node, Vite, Deno, Bash | Unset |
| Go | Fails to load the file |

The loaders that miss `PORT` read the BOM as part of its name, so they set a variable nobody asks for. Go stops with `unexpected character "»" in variable name` and sets nothing. Every loader except Go still read `APP` on the second line, so the bug shows up only as one missing variable. Save the file as UTF-8 without a BOM.

### A value your shell already set

With `PORT=4000` exported in the shell and `PORT=3000` in the file:

| Loader | `PORT` |
| --- | --- |
| The nine library loaders | `4000`, the shell |
| Bash, Compose `env_file` | `3000`, the file |

Libraries such as dotenv, python-dotenv and Node's flag never overwrite a variable that is already set, and dotenv and python-dotenv have an `override` option if you want the file to win. Sourcing a file in Bash is a series of assignments, so the file wins. In Compose, a file named in `env_file` goes into the container even when your shell sets the same name, as the [Docker Compose .env guide](/blog/docker-compose-env-file) shows.

## A .env file that reads the same in all 11

Put the agreed rules together and you get a file every loader reads identically. Here is one for a small app called Acme notes. Every value is fake.

```bash title=".env"
# Acme notes, local development. Every value here is fake.
APP_NAME="Acme notes"
PORT=3000
DEBUG=true

# Database
DATABASE_URL=postgres://localhost:5432/acme_dev

# Third-party services
PAYMENTS_API_KEY=fake-key-for-local-dev
SENTRY_DSN=
```

We loaded this exact file with all 11 loaders, and every one printed the same six values:

```text title="Output"
APP_NAME="Acme notes"
PORT="3000"
DEBUG="true"
DATABASE_URL="postgres://localhost:5432/acme_dev"
PAYMENTS_API_KEY="fake-key-for-local-dev"
SENTRY_DSN=""
```

Download the [sample .env](/blog/env-file/sample.env) and its matching [.env.example](/blog/env-file/sample.env.example). The rules behind it:

- One variable per line, as `PORT=3000`, with no spaces around `=`.
- Names use letters, digits and `_`, uppercase by convention.
- Comments go on their own line.
- Values with a space or `#` go in double quotes, as `APP_NAME="Acme notes"`.
- Values contain no `$` and no references to other variables.
- Multi-line values use real line breaks inside double quotes, never `\n`.
- Each name appears once.
- The file is UTF-8 without a BOM, with LF line endings.

## .env vs .env.example vs the environment

Three things share the name, and they have different jobs:

- **`.env`** holds your real values for this machine. Add it to `.gitignore` and never commit it.
- **`.env.example`** lists every variable name the app needs, with empty or safe defaults. Commit it, since it documents the configuration.
- **The process environment** is what the running app sees, from the shell, the host or a loader. It isn't a file, and your host or CI sets it in production.

`.env.example` is the file a new teammate copies after cloning. Keep it in step with `.env` whenever you add a variable, and leave real secrets out of it, since it lives in Git history forever.

In production, you usually skip the file entirely. Hosting platforms, containers and CI systems all have their own way to set environment variables, and the app reads them the same way.

## How to create and load a .env file

<Steps>
<Step>

### Copy the example

From the project root, copy the template and keep `.env` out of Git:

```bash title="Terminal"
cp .env.example .env
echo ".env" >> .gitignore
```

If the repository has no `.env.example`, check its README or the code for `process.env` and `os.environ` to find the names it expects.

</Step>
<Step>

### Fill in your values

Open `.env` and set each value with the rules above: no spaces around `=`, double quotes around anything with a space or `#`, and no `$`.

</Step>
<Step>

### Load it

Pick the loader for your runtime.

<Tabs items={["Node.js", "Bun", "dotenv", "Python"]}>
<Tab value="Node.js">

Node 20.6 and later read the file with a flag. It's stable since 22.21 and 24.10.

```bash title="Terminal"
node --env-file=.env server.js
```

Use `--env-file-if-exists=.env` when the file is optional, for example in CI.

</Tab>
<Tab value="Bun">

Bun loads `.env`, `.env.local` and `.env.<NODE_ENV>` automatically, with no code.

```bash title="Terminal"
bun server.ts
```

Pass `--no-env-file` to turn that off in production.

</Tab>
<Tab value="dotenv">

For older Node versions or tools that don't take flags, load it in code before anything reads the environment:

```js title="server.js"
require("dotenv").config()
```

</Tab>
<Tab value="Python">

Install `python-dotenv`, then load it at the top of your entry point:

```python title="app.py"
from dotenv import load_dotenv

load_dotenv()
```

</Tab>
</Tabs>

</Step>
<Step>

### Check what the app sees

Print one value to confirm the file loaded:

```bash title="Terminal"
node --env-file=.env -p "process.env.APP_NAME"
```

```text title="Output"
Acme notes
```

</Step>
</Steps>

## How to share .env values with your team

The file stays on your machine, so the hard part is getting the real values to the next person without pasting them into a chat. These are the common options, from least to most setup:

- **A password manager or one-time link** fits when one person needs the values once. Nothing updates when a value changes.
- **An encrypted file in Git**, with dotenvx or SOPS, fits a team that shares a key and wants values versioned with the code. Rotating the key touches every file.
- **A secrets manager**, such as Doppler or Infisical, fits when you need audit logs, rotation and per-environment access rules, and the setup pays off.
- **A Sniptide env group** fits a solo developer or small team that wants the values next to their shared code and pulled with one command.

### Push your .env once

```bash title="Terminal"

```

This creates the env group `acme-notes` from `./.env`. A push replaces the whole group, so a variable you deleted from the file is deleted from the group too.

</Step>


## When the .env file isn't loading

- **The app reads `undefined`.** Nothing loaded the file. Check that you passed `--env-file`, called `config()` before the code that reads the value, or that the runtime loads it on its own.
- **The file is in the wrong folder.** Loaders look in the current working directory, which isn't always the folder of the script. Run the command from the project root, or pass the full path.
- **An old value sticks.** The shell already exports that name. Run `echo $PORT`, then `unset PORT` or open a new terminal.
- **A value is cut short.** It contains `#` or `$`. Put it in double quotes, and test any `$` with the loader you deploy with.
- **The first variable is missing.** The file starts with a byte order mark. Save it again as UTF-8 without a BOM.
- **A value doesn't match although it looks right.** The file has Windows line endings and something sources it with Bash. Convert it to LF.
- **The file is named `.env.txt`.** Some editors add an extension. Show file extensions and rename it to exactly `.env`.
